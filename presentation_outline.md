# Presentation Outline

## Slide 1: Title

Query Processing over Streaming Data using Apache Flink  
Yun Hanxu, CSIT6910 Independent Project

## Slide 2: Motivation

Analytical queries are often needed over data that keeps changing. Rerunning a multi-table SQL query after every update is expensive. Continuous query processing maintains the answer incrementally and emits only the changes.

## Slide 3: Project Requirement

The project uses TPC-H, selects a query with at least three tables, implements the update algorithm in Flink, verifies correctness with a standard database, and evaluates basic performance.

## Slide 4: Selected Query

TPC-H Q3 joins `customer`, `orders`, and `lineitem`. It filters by market segment and dates, then groups by order key, order date, and ship priority to compute revenue.

## Slide 5: Why Q3

Q3 is the query highlighted in the Cquirrel demo and the project briefing. It includes three-table foreign-key joins and aggregation, while remaining manageable for a focused prototype.

## Slide 6: Cquirrel/AJU Algorithm

Use the foreign-key DAG `lineitem -> orders -> customer`. Maintain each tuple's
live flag and child-match count bottom-up. Only a lineitem that transitions
into or out of the live root set changes a revenue group. No intermediate join
result is materialized.

## Slide 7: System Design

Ordered input -> sequence assignment -> order-shard routing -> keyed process
function -> delta output.

Orders and lineitems are partitioned by order key. Customer changes are copied
to every shard. Each shard owns Flink managed state:

```text
customers
orders
ordersByCustomer
lineItemsByOrder
live flags and child-match counts
```

The ordered global stage combines shard responses, stores exact fixed-point
group revenue, and maintains the official Q3 Top-10.

## Slide 8: Demo Update Format

```text
+|customer|1|BUILDING
+|orders|100|1|1995-03-01|0
+|lineitem|100|1|1000.00|0.05|1995-03-20
-|lineitem|100|1
```

## Slide 9: Output Format

```text
sequence|change_type|l_orderkey|o_orderdate|shippriority|delta|current|reason
```

The output is delta enumeration: only changed groups are printed. A complete
Top-10 is emitted only when its ranking changes.

## Slide 10: Correctness Verification

Replay the same update stream into SQLite using exact integer arithmetic.
Reconstruct the complete Flink state from deltas and compare every group at
selected snapshots, plus every emitted Top-10. The SF0.1 run passes 12 full
snapshots and all 141 ranking changes.

## Slide 11: Benchmark Setup

Use both update-heavy synthetic streams and TPC-H SF0.1 tables generated by
the TPC-H-compatible dbgen extension. The deterministic FIFO stream contains
1,140,816 insertions and deletions. Use one warm-up and three measured runs at
parallelism 1, 2, 4, and 8, and reject a run unless every worker is active.

## Slide 12: Experimental Results

Mean internal processing throughput is 654,465 updates/s at parallelism 1,
895,124 at parallelism 2, 828,483 at parallelism 4, and 756,174 at
parallelism 8. All configured workers process non-zero records. Parallelism 4
has the lowest median latency, 3,197 microseconds.

## Slide 13: Limitations

The prototype supports Q3 rather than arbitrary SPJA queries. Customer updates
are replicated and exact sequence ordering plus Top-10 maintenance uses one
global stage. Results are local bounded-file measurements, not audited TPC
benchmark results. Managed state is checkpointed, but the console sink is not
transactional.

## Slide 14: Future Work

Evaluate a long-running Kafka source and a Flink cluster, reduce customer
replication with a subscription index, use a transactional sink for
failure-injection tests, and extend the compiler to more TPC-H queries.

## Slide 15: Conclusion

The project implements continuous maintenance of a three-table analytical query in Flink. It demonstrates how incremental update processing can avoid full recomputation and produce real-time query-result changes.
